# Архитектура CheckStock

## Цель

Небольшой модульный монолит, который можно реализовать и объяснить за один день.
Он обеспечивает атомарный складской учёт, но не имитирует production-систему
маркетплейса и не содержит функций из большого проекта Raketa.

```text
React + TypeScript
        |
        | HTTP/JSON
        v
FastAPI routes -> application services -> repositories -> PostgreSQL
                         |
                         +-> operation ledger / idempotency
```

## Backend

```text
backend/app/
├── api/            # HTTP-роуты и зависимости
├── core/           # конфигурация, БД, логирование, ошибки
├── domain/         # статусы, инварианты и доменные типы
├── models/         # SQLAlchemy-модели
├── repositories/   # запросы и блокировки строк
├── schemas/        # Pydantic-контракты API
├── services/       # транзакционные use cases
└── main.py
```

Роут не изменяет остатки напрямую. Сервис открывает одну транзакцию, блокирует
нужные строки остатков, проверяет инварианты, изменяет состояние и пишет событие
в журнал. Репозиторий не принимает бизнес-решения.

## Frontend

```text
frontend/src/
├── app/            # композиция приложения и маршруты
├── features/       # inventory, warehouses, operations
├── shared/api/     # единый HTTP-клиент
├── shared/ui/      # общие состояния и элементы
└── main.tsx
```

Для тестового достаточно одного рабочего экрана с вкладками или секциями:
остатки, действия и история. Состояние сервера не дублируется в сложном global
store; после команды нужные данные перечитываются.

## Модель данных

### `products`

- `id` UUID;
- `sku` unique;
- `name`;
- `created_at`.

### `warehouses`

- `id` UUID;
- `name` unique среди активных;
- `archived_at` nullable;
- timestamps.

Удаление — soft delete. Остаток и история продолжают ссылаться на склад.
Архивный склад отображается в остатках, но не принимает новые приходы, резервы
и отправки. Разрешается только перемещение существующего товара из него.

### `inventory_balances`

- `product_id`, `warehouse_id` — составной unique;
- `on_hand` — физически на ФФ;
- `reserved_fbs` — заблокировано под FBS;
- `version` — оптимистическая диагностика изменений;
- `updated_at`.

`available` не хранится: `on_hand - reserved_fbs`.

### `transfers`

- товар, количество, source и destination;
- status: `draft | in_transit | received`;
- `dispatched_at`, `received_at`.

При отправке уменьшается `on_hand` источника. При приёмке увеличивается
`on_hand` назначения. Количество в статусе `in_transit` показывается отдельно.
Черновик можно удалить до отправки: остатки не меняются, а событие удаления
сохраняется в журнале. Отправленные и принятые перемещения не удаляются.

### `fbs_reservations`

- товар, ФФ, количество;
- status: `reserved | cancelled | shipped`;
- timestamps.

Резерв увеличивает `reserved_fbs`. Отмена уменьшает только резерв. Отправка
одновременно уменьшает `reserved_fbs` и `on_hand`; отправленное количество
показывается как едущее клиенту.

### `fbo_shipments`

- товар, ФФ, количество;
- status: `in_transit | received`;
- timestamps.

Создание отправки уменьшает `on_hand` ФФ. До приёмки количество показывается
как едущее на склад маркетплейса.

### `operations`

Append-only журнал: тип, товар, количество, source/destination, сущность,
метаданные и время. Он нужен для объяснимой истории, а не для пересчёта баланса.

### `idempotency_records`

Хранит уникальный ключ команды, тип операции, статус и сохранённый ответ.
Повтор с тем же ключом и тем же payload возвращает исходный результат. Тот же
ключ с другим payload возвращает `409 Conflict`.

## Инварианты

- `on_hand >= 0`;
- `reserved_fbs >= 0`;
- `reserved_fbs <= on_hand`;
- количество команды — целое число больше нуля;
- source и destination перемещения различаются;
- остаток другого ФФ нельзя автоматически использовать для выбранного ФФ;
- завершённую операцию нельзя подтвердить второй раз;
- каждое изменение баланса и запись истории фиксируются одной транзакцией.

## Конкурентность

Перед списанием сервис выполняет `SELECT ... FOR UPDATE` для конкретной пары
`product_id + warehouse_id`. Для перемещения блокировки берутся в стабильном
порядке идентификаторов, чтобы уменьшить риск deadlock.

## Осознанно не добавляем

- Redis и очередь задач;
- микросервисы и event bus;
- авторизацию и роли;
- реальную интеграцию WB/Ozon;
- прогнозирование и закупки;
- Kubernetes и production monitoring.

Это не требуется тестовым и ухудшит шанс закончить основной сценарий за день.
