# CheckStock

Рабочий прототип складского учёта для продавца на маркетплейсах. Он отвечает на
главный вопрос «где сейчас товар?» и проводит товар через приёмку, перемещение,
FBS-резерв и FBO-отправку без двойных списаний.

## Что реализовано

- остатки по SKU и складам: физически, в резерве и доступно;
- приёмка товара;
- двухэтапное перемещение: черновик → отправка → приёмка;
- FBS: резерв → отмена или отгрузка клиенту;
- FBO: отправка → подтверждение приёмки маркетплейсом;
- отдельный учёт товаров в пути;
- создание, переименование и мягкое удаление складов;
- журнал операций с фильтрами;
- понятная ошибка дефицита на выбранном складе;
- защита команд от повторного выполнения через `Idempotency-Key`;
- загрузка, empty/error-состояния, retry и адаптивный интерфейс.

## Быстрый запуск

Нужен только Docker с Compose.

```bash
make setup
docker compose up --build
```

`make setup` создаёт `.env` и записывает в него случайный пароль PostgreSQL.
Готовый `.env` не должен попадать в Git. Если окружение настраивается вручную,
скопируйте `.env.example` и обязательно заполните `POSTGRES_PASSWORD`.

При первом запуске backend применит миграции и идемпотентно добавит тестовые
товары, склады и остатки.

- приложение: http://localhost:5173;
- Swagger: http://localhost:8000/docs;
- health: http://localhost:8000/api/health;
- PostgreSQL с хоста: `localhost:55433` (доступен только локально).

Порт БД намеренно отличается от стандартного `5432`, чтобы не конфликтовать с
локальным PostgreSQL.

## Проверки

```bash
make test
make lint
cd frontend && npm run build
```

Backend-тесты создают отдельную временную схему PostgreSQL и удаляют её после
прогона. Это позволяет проверять настоящие транзакции и `SELECT FOR UPDATE`, в
том числе два параллельных резерва одного остатка.

Покрыты: seed, приёмка, перемещение, FBS/FBO, дефицит, архивирование склада,
идемпотентность, история и конкурентное списание.

## Архитектура

```text
React + TypeScript
        │ HTTP/JSON
        ▼
FastAPI routes
        ▼
application services ── operation ledger / idempotency
        ▼
repositories
        ▼
PostgreSQL
```

Это модульный монолит: для объёма тестового он проще в запуске и сопровождении,
чем набор сервисов, но границы API, сценариев и хранения отделены друг от друга.
Роуты не меняют остатки напрямую. Сервис выполняет проверку, блокировку баланса,
изменение состояния и запись истории в одной транзакции.

Frontend разбит по бизнес-функциям. Сложный глобальный store не добавлялся:
после подтверждённой команды клиент перечитывает серверное состояние.

Подробности: [архитектура](docs/architecture.md),
[спецификация](docs/specification.md), [API](docs/api.md).

## Ключевые решения и компромиссы

### Остаток

`available` не хранится отдельно и вычисляется как
`on_hand - reserved_fbs`. Это исключает рассинхронизацию трёх чисел.

### Перемещения и отправки

Товар списывается с исходного склада в момент отправки и до приёмки учитывается
отдельно как находящийся в пути. Поэтому один и тот же товар не показывается
одновременно на складе и в транзите.

### Удаление склада

Удаление реализовано как архивирование. История и остатки сохраняются, новые
приходы и отправки запрещаются. Остаток можно вывести перемещением на активный
склад.

### Надёжность команд

Перед списанием строка остатка блокируется через `SELECT FOR UPDATE`. В БД также
есть ограничения `on_hand >= 0`, `reserved_fbs >= 0` и
`reserved_fbs <= on_hand`. Команды подтверждения используют уникальный ключ
идемпотентности: точный повтор возвращает прежний ответ, а повтор ключа с другим
запросом завершается конфликтом.

### Границы прототипа

Реальные API Wildberries/Ozon, авторизация, фоновые очереди, прогнозирование,
закупочная потребность и production-мониторинг не добавлялись: они относятся к
большому проекту Raketa, но не требуются в тестовом CheckStock.

## Использование AI-инструментов

При разработке использовался Codex как инженерный агент: для разбора ТЗ,
формализации инвариантов, подготовки структуры проекта, реализации и запуска
проверок. Работа велась короткими проверяемыми этапами: спецификация → модель
данных → API и тесты → интерфейс → аудит.

Решения по границам задачи, трактовке FBS/FBO, моментам списания, soft delete,
идемпотентности и критериям готовности фиксировались до генерации кода. Результат
проверялся тестами, линтерами, production-сборкой и ручным прогоном интерфейса.
